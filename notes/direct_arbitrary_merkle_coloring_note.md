# 保留 Swapped 视角的任意 Merkle 树染色

## 1. 修正后的核心方向

你的判断是对的：

- `swapped tree` 的想法应该保留；
- 这样才能继续使用“祖先染色”这条主线；
- 目标 proof 在 swapped 视角下仍然是一条 root-to-leaf 路径；
- 客户端就能继续按“颜色 + 子库索引”来做 batch-PIR；
- 但空节点不进入子库，子库里只保存真实需要私有检索的节点。

所以更准确的表述不是“放弃 swap”，而是：

> 保留 `swapped` 作为逻辑查询视图，但不物化整棵 perfect/swapped tree；只把真实 proof-bearing node 放进数据库。

这比“先压缩后染色”更贴近原始数据结构，也比“直接对所有默认空节点染色”更可实现。

## 2. 模型：Virtual Swapped Sparse Merkle Tree

设原始 Merkle 树为 `T`，叶子按照从左到右编号。

对 `T` 做与 TreePIR 相同的 sibling-swap，只不过这里：

- swap 只是**逻辑上的**
- 不要求真的重建一棵完整的新树
- 也不要求把空子树的默认节点存进子库

我们只保留一类节点：

`active proof-bearing node`

也就是：

- 它会在至少一个真实叶子的 membership proof 中出现；
- 或等价地，在 swapped 视角下，它位于至少一条真实查询路径上。

如果某一层对应的兄弟子树完全为空，那么该层 proof 元素是公开可重建的默认哈希，不需要进入 PIR 数据库。

因此，数据库中保存的是：

- 原始树上真实存在、并且对某些 proof 真的有贡献的节点；
- 每个节点只保存一次；
- 没有空节点，没有副本。

## 3. 为什么祖先染色仍然成立

在 perfect tree 的 TreePIR 里，swap 的作用是：

- 把“proof 的兄弟节点集合”变成“swapped tree 上的一条路径”。

在这里，这个逻辑仍然成立，只是路径会变成一条“稀疏路径”：

- 某些层有真实节点，要查询；
- 某些层只有默认空节点，直接跳过；
- 因此真实查询对象是 swapped 路径上的一个子序列。

于是祖先染色条件自然变成：

> 任何一条真实 swapped proof 路径上，所有被存入子库的真实节点颜色必须互不相同。

这保留了 TreePIR 最核心的结构意义。

## 4. 与区间模型的关系

我之前写的区间模型并不是和 `swap` 对立，它其实可以理解为：

- `swap` 给出了“proof 是路径”的几何结构；
- `interval` 给出了“如何在每个颜色子库里快速索引这条路径上的那个节点”。

更具体地说：

对每个非根真实节点 `u`，定义它对应的叶区间

`I(u) = sibling(u)` 所覆盖的真实叶区间。

那么：

- `u` 出现在叶 `x` 的 proof 中，当且仅当 `x in I(u)`；
- 同一个 proof 上的节点，在 swapped 视角下是一条路径；
- 在区间视角下，对应一条“按包含关系嵌套的区间链”。

所以：

- `swap/path` 是**染色语义**
- `interval` 是**索引工具**

这两个视角其实是等价且互补的。

## 5. 新的建议算法

可以把新方案写成：

`Sparse-Swapped TreePIR`

或者

`Virtual-Swapped Ancestral Coloring for Arbitrary Merkle Trees`

### 输入

- 一棵固定的任意二叉 Merkle 树 `T`
- 真实叶集合 `L`
- 所有默认空子树的公开可重建哈希

### 预处理

1. 对 `T` 采用 TreePIR 的 swapped 视角；
2. 删除所有不会出现在任何真实 proof 中的空节点；
3. 只保留 active proof-bearing node；
4. 对这些节点做祖先染色。

### 染色约束

若两个 active node 会同时出现在某个真实叶子的 proof 中，则它们不能同色。

在 swapped 视角下，这等价于：

- 同一条真实 swapped 路径上的节点颜色互异。

### 颜色数

取

`m = 最大真实 proof 长度`

也就是任意真实叶的 swapped 活跃路径里，真实节点的最大数量。

### 查询

对目标叶 `x`：

- 对每个颜色 `c = 1,...,m` 发送一次 PIR；
- 若颜色 `c` 在 `x` 的真实 proof 上有节点，则查询其子库索引；
- 否则发送 dummy 查询。

这样总查询数恒定为 `m`，不会泄露路径长短。

## 6. 为什么这样比“压缩后再染色”更有意义

这个版本的优势是：

- 不改变原始数据组织；
- 保留 TreePIR 的 swapped-path 解释；
- 不保存空节点；
- 不需要把整个数据结构改造成 perfect full tree；
- 子库中只有真实数据，工程上更自然。

从论文意义上说，它比“压缩树后再做”更强，因为你是在证明：

> TreePIR 的祖先染色思想可以从 perfect tree 推广到任意固定 Merkle 树，只要把 swap 保留为逻辑视图，并忽略公开可重建的空节点。

## 7. 索引为什么仍然简单

每种颜色对应一个子库。

为了让客户端找到“某颜色下该查哪个真实节点”，可以用区间索引：

- 对每个颜色类，把节点按叶区间左端点排序；
- 由于同色节点不可能出现在同一条 proof 上，所以同色区间必然不重叠；
- 对目标叶 `x`，在每个颜色类中做一次二分即可找到唯一真实节点；
- 找不到就是 dummy。

因此索引复杂度可以写成：

`O(m log |C_i|)` 每色一次二分，

总共约为

`O(m log N)`

这里：

- `m` 是最大真实 proof 长度
- `N` 是 active proof-bearing node 总数

这已经比 perfect-tree 版本里围绕颜色分裂序列做的专门索引更容易落地。

## 8. 安全性怎么说

只要底层 PIR 安全，那么这个方案的安全性论证基本沿用 TreePIR：

- 每个颜色子库都发一次查询；
- 真实节点与 dummy 节点在查询模式上不可区分；
- 查询总数固定为 `m`；
- 空节点不入库不会泄露信息，因为默认空哈希本来就是公开可重建的。

因此隐藏的是：

- 目标叶是哪一个真实叶；
- 目标 proof 中哪些层是“真实查询层”、哪些层是 dummy。

## 9. 可以写成论文的主张

这条线可以整理成下面这种表述：

### 命题 1

对任意固定二叉 Merkle 树，在 virtual swapped 视角下，所有真实 proof-bearing node 的冲突关系可由真实 proof 路径上的共现关系刻画。

### 命题 2

若一种染色满足任意真实 swapped proof 路径上颜色互异，则客户端可通过“每色一次 PIR + dummy 补齐”的方式私有检索 proof。

### 命题 3

若同色节点按叶区间索引，则对任意目标叶，每种颜色至多对应一个真实候选节点，因此客户端可用二分搜索得到子库索引。

### 优化目标

在满足上述约束下，最小化：

- 最大子库大小
- 或加权负载不平衡度
- 或通信与服务器计算的联合成本

## 10. 当前代码应如何理解

当前原型文件：

- `direct_arbitrary_merkle_coloring.py`

它虽然没有显式构造整棵 swapped tree，但本质上已经在做下面这件事：

- 用 proof interval 来表示 swapped 路径上的活跃节点；
- 用区间包含关系来模拟祖先路径；
- 用颜色类上的区间索引来模拟“颜色 + 位置”的查询方式。

所以它更适合被解释为：

> `virtual swapped sparse TreePIR` 的一个索引驱动实现原型。
