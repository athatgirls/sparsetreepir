# Xenon Sparse-SMT Real-Data Backend Experiment

## Goal

Move beyond purely random synthetic trees and evaluate the sparse-SMT retrieval layer on a real public dataset source. We use the Xenon 2024 certificate-log dump as the source of real keys, derive sparse-SMT snapshots from it, and then compare:

- `perfectized_treepir`
- `hybrid`
- `profile_balanced`

The purpose of this experiment is not yet to claim production PIR throughput, but to answer a more basic and important question:

> when the key set comes from a real dataset rather than a synthetic generator, does the direct sparse-SMT organization still keep storage small and improve color-bucket balance?

## Dataset

- dataset path: `c:\Users\15313\Downloads\xenon2024_log_entries`
- parsed field: `entry_number`
- unique values in earlier scan: `1,048,574`
- observed range: `[0, 1,048,575]`

The Xenon entry numbers are almost contiguous. To turn them into sparse-SMT addresses, we use two mappings:

- `sequential`: preserve the original order and map directly into the address space
- `sha256`: hash the real entry number and map it into the address space

These two mappings give two complementary real-data scenarios:

- `sequential` is a real but highly clustered/ordered stress case
- `sha256` is a real-key hashed-address case, closer to content-addressed sparse placement

## Setup

- sparse SMT height: `20`
- occupied snapshot sizes: `5000`, `10000`, `20000`
- hybrid initialization rounds: `60`
- profile refinement rounds: `3`
- backend query samples per snapshot: `6`

Command template:

```powershell
python scripts\run_xenon_sparse_smt_backend_experiment.py `
  --height 20 `
  --sizes 5000,10000,20000 `
  --address-mode sha256 `
  --rounds 60 `
  --profile-rounds 3 `
  --query-samples 6
```

and similarly for `--address-mode sequential`.

## Direct comparison against the perfectized baseline

For all snapshots at height `20`, the perfectized baseline uses:

- protocol colors: `20`
- stored nodes: `2,097,150`

By contrast, the direct sparse-SMT schemes store only:

- `9,998` nodes at `5000` occupied leaves
- `19,998` nodes at `10000` occupied leaves
- `39,998` nodes at `20000` occupied leaves

This is only:

- `0.48%`
- `0.95%`
- `1.91%`

of the perfectized storage, respectively.

At the same time, the direct sparse-SMT batch width is also smaller:

- `14` to `18` colors for the direct schemes
- versus `20` colors for the perfectized baseline

## Takeaways

### 1. The “real experiment” story is now materially stronger

These snapshots are no longer generated by a synthetic tree sampler. The key source is a real certificate-log dataset, and the sparse-SMT structure is induced by real entries.

### 2. `profile_balanced` still improves bucket balance on real data

The improvement is not limited to random synthetic trees. On real Xenon-derived snapshots:

- it consistently reduces the largest count imbalance
- the effect remains strong under both hashed and ordered address mappings

### 3. Count balance and weighted balance diverge on clustered real layouts

The `sequential` mapping is especially useful because it exposes a real weakness:

- `profile_balanced` improves count balance strongly
- but may not improve weighted balance at the same time

This is a useful and honest result. It shows that real clustered data stresses the forest differently from random inputs, and it confirms that count-balance and weighted-balance are genuinely different objectives.

### 4. Real-data structure helps more than backend constants hurt

Even though the current PIR backends are still executable surrogates rather than production SealPIR/Spiral implementations, the structural reduction is already dramatic:

- direct sparse organization stores orders of magnitude fewer nodes than the perfectized baseline
- the required batch width also drops below the full height

So the main structural signal survives when the key set comes from real data.

## Recommended paper usage

This experiment is best presented as:

> a real-data structural-and-backend sanity check on Xenon-derived sparse-SMT snapshots

rather than as a final production-system benchmark.

That framing is accurate and still valuable.
