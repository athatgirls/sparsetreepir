\title{SparseTreePIR: Active-Interval Coloring for Batch Private Information Retrieval of Sparse Merkle Proofs}

\author{\IEEEauthorblockN{Anonymous Author(s)}}

\begin{document}

\maketitle

\begin{abstract}
Sparse Merkle Trees (SMTs) support compact membership proofs over large logical address spaces by combining real sibling digests with public default-empty hashes, but ordinary proof serving reveals the queried coordinate and its authenticated path. We study fixed-snapshot SMT membership-proof retrieval as a target-private batch-PIR workload. The key question is not which PIR primitive to use, but what PIR-facing database a sparse proof induces. SparseTreePIR answers this question by characterizing the active proof-bearing interval forest: the minimal set of non-default sibling digests needed to serve all occupied-leaf membership proofs under public default completion. The construction places only those records in PIR subdatabases, indexes them by served target-leaf intervals, colors the interval forest so that each proof issues exactly one query per active color, and lets the client complete the standard height-$h$ SMT proof locally from public default hashes. Thus the verifier-facing proof length remains height $h$, while the PIR-facing query width is the active width, not the logical height. We further introduce \ActiveBalance{}, a subtree-load refinement that preserves the fixed transcript while reducing the largest color store and producing an instance-wise balance certificate. On six SMT workloads, the active width is only $9$--$17$ even for height-$128$ and height-$256$ proofs. Against a direct Pruned TreePIR-$h$ baseline that deletes default records but keeps the height-$h$ query universe, SparseTreePIR uses $9.5\times$ fewer subqueries and a $2.5\times$ smaller largest searched store on height-$128$ workloads. It also uses $1.5\times$ fewer subqueries than an optimistic PBC-style SMT baseline and a $12.7\times$ smaller searched database than flat active PIR. Executable SimplePIR and PIANO runs show $2.1\times$--$2.3\times$ lower online communication, with a $1.8\times$ lower SimplePIR server-answer time, without changing the underlying PIR primitive.
\end{abstract}
